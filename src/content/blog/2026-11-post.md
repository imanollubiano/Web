## Introducción

PowerShell ha evolucionado desde ser una simple herramienta de scripting a convertirse en el estándar de facto para automatización en infraestructuras Windows. La capacidad de ejecutar comandos de forma remota mediante WinRM (Windows Remote Management) es crítica para cualquier sysadmin que maneje más de una docena de servidores. Este artículo aborda las implementaciones avanzadas y patrones de producción que transforman PowerShell en un orquestador eficiente.

## Configuración base de WinRM y consideraciones de seguridad

WinRM es el protocolo subyacente que permite la comunicación remota en PowerShell. Por defecto, en sistemas Windows Server modernos viene deshabilitado o parcialmente configurado. La configuración incorrecta es la causa raíz del 60% de los problemas de remoting en entornos empresariales.

### Inicialización segura de WinRM

El servicio WinRM debe ejecutarse bajo el contexto correcto y con certificados SSL/TLS validados. En producción, evitar HTTP en texto plano es no negociable:

```powershell
# Verificar estado del servicio
Get-Service WinRM | Select-Object Status, StartType

# Inicializar WinRM con soporte HTTPS
winrm quickconfig -quiet

# Crear listener HTTPS con certificado válido
$cert = Get-ChildItem -Path Cert:\LocalMachine\My | Where-Object {$_.Subject -match "CN=servidor.dominio.local"}

New-WSManInstance -ResourceURI winrm/config/Listener -SelectorSet @{Address="*";Transport="HTTPS"} `
  -ValueSet @{CertificateThumbprint=$cert.Thumbprint;Enabled=$true}

# Configurar autenticación: Kerberos en dominio, Negotiate como fallback
Set-Item -Path WSMan:\localhost\Service\Auth\Kerberos -Value $true
Set-Item -Path WSMan:\localhost\Service\Auth\Negotiate -Value $true
Set-Item -Path WSMan:\localhost\Service\Auth\Basic -Value $false
```

La negación de Basic Auth es crítica. Aunque Negotiate permite fallback automático, Basic transmite credenciales en base64, que es equivalente a texto plano.

## Gestión avanzada de sesiones remotas

Las sesiones remotas de PowerShell son entidades persistentes que optimizan múltiples ejecuciones. Crear y reutilizar sesiones reduce overhead de autenticación en un 70-80%.

### Patrones de sesión persistent

```powershell
# Crear sesión persistente con opciones de configuración
$options = New-PSSessionOption -OperationTimeout (15*60*1000) `
  -IdleTimeout (30*60*1000) `
  -MaxConnectionRetryCount 3 `
  -NoMachineProfile $true

$session = New-PSSession -ComputerName srv-prod-01, srv-prod-02 `
  -Authentication Kerberos `
  -SessionOption $options `
  -ConfigurationName Microsoft.PowerShell `
  -ErrorAction Stop

# Pool de sesiones para ejecución paralela
$servers = @("srv-01", "srv-02", "srv-03", "srv-04", "srv-05")
$sessions = New-PSSession -ComputerName $servers -Authentication Kerberos

# Invocar comando en paralelo
$result = Invoke-Command -Session $sessions -ScriptBlock {
    Get-Process | Where-Object {$_.WorkingSet -gt 500MB} | Select-Object PSComputerName, Name, WorkingSet
} -ThrottleLimit 5

# Limpiar sesiones
Get-PSSession | Remove-PSSession
```

La opción `-NoMachineProfile` acelera la inicialización en 200-300ms porque evita cargar perfiles de usuario completos. En automatización masiva, esto suma significativamente.

## Delegación de credenciales y CredSSP

El escenario clásico: necesitas ejecutar un comando remoto que a su vez se conecta a otro servidor remoto (double-hop). NTLM falla aquí por diseño; Kerberos requiere delegación; CredSSP es la solución pero con costos de seguridad.

### Configurar CredSSP de forma segura

En el cliente (máquina desde la que ejecutas):

```powershell
# Habilitar CredSSP solo para hosts específicos
Enable-WSManCredSSP -Role Client -DelegateComputer "srv-prod-*.dominio.local" -Force

# Crear sesión con CredSSP
$cred = Get-Credential
$session = New-PSSession -ComputerName srv-prod-01 `
  -Authentication CredSSP `
  -Credential $cred `
  -SessionOption (New-PSSessionOption -OperationTimeout (20*60*1000))

# Verificar configuración
Get-WSManCredSSP
```

En el servidor (máquina remota):

```powershell
Enable-WSManCredSSP -Role Server -Force
```

**Advertencia crítica**: CredSSP almacena credenciales en memoria del servidor remoto durante la sesión. Usar solo con servidores de confianza absoluta y supervisados.

## Remoting a escala: patrones de distribución

Con 500+ servidores, la ejecución serial es impráctica. Los patrones de distribución con throttling son esenciales.

### Procesamiento por lotes con manejo de errores robusto

```powershell
$servers = Get-Content .\servers.txt
$batchSize = 20
$failed = @()
$results = @()

for ($i = 0; $i -lt $servers.Count; $i += $batchSize) {
    $batch = $servers[$i..([Math]::Min($i + $batchSize - 1, $servers.Count - 1))]
    
    try {
        $batchResults = Invoke-Command -ComputerName $batch `
          -ScriptBlock {
              [PSCustomObject]@{
                  Host = $env:COMPUTERNAME
                  FreeSpace = (Get-Volume | Where-Object DriveLetter -eq C | Select-Object -ExpandProperty SizeRemaining) / 1GB
                  Timestamp = Get-Date
              }
          } -ErrorAction Continue -AsJob
        
        $results += $batchResults | Wait-Job | Receive-Job
        
    } catch {
        $failed += $batch
        Write-Warning "Lote fallido: $($batch -join ', ')"
    }
}

$results | Export-Csv -Path .\report.csv -NoTypeInformation
Write-Host "Completados: $($results.Count), Fallidos: $($failed.Count)"
```

El parámetro `-AsJob` permite paralelización real con control fino. `ThrottleLimit` en Invoke-Command funciona mejor que Wait-Job para escenarios masivos.

Los problemas de remoting raramente son obvios. El logging de WinRM es fundamental:

# Habilitar logging detallado de WinRM
Set-PSDebug -Trace 2

# Verificar conectividad preliminar
Test-WSMan -ComputerName srv-prod-01 -Authentication Kerberos

# Revisar eventos del sistema
Get-EventLog -LogName System -Source WinRM -Newest 50 | Where-Object {$_.EventID -ge 10000}
